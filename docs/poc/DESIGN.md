# Customer PoC: .NET Framework 4.8

Two IIS-hosted ASP.NET .NET Framework 4.8 applications share OWIN OpenID Connect and direct MSAL.NET authorization-code redemption with PKCE. Katana retains protected state and nonce validation; the strict JWT handler requires a signed ID token, expected signing key, issuer, audience and lifetime. Each app has a single-tenant registration in each directory, separate callbacks and credentials. Application cookies are distinct, Secure and HttpOnly.

Role mapping: app01 workforce `Employee`; app02 workforce `Employee`, `Partner`, `admin`, `dependentRegistrant`; both external clients `Retiree`, `Dependent`, `External`. The capability roles supplement an approved workforce Employee; they do not replace the persona or app approval. App01 admits no Partner.

An email is a routing hint, never identity evidence. Employee domains and explicitly onboarded partner routes go to the workforce tenant. Other accounts go to External ID. The token issuer, audience, tenant, signature and stable subject establish identity. There is no fallback after a failed workforce authentication. Partner B2B onboarding must verify the home organization; an arbitrary Gmail guest is not a Microsoft 365 partner. External-tenant Entra OIDC federation is a documented alternative for partners whose lifecycle must live in External ID.

Sponsored registration treats exact known consumer-provider domains, including `gmail.com`, as personal External ID identities without organizational discovery. A discovery response for another domain supplies only a candidate home tenant; signed home-issuer evidence and approved app02 governance are still required. Neither an organizational email nor a signed organizational identity proves a Microsoft 365 product license.

Application admission uses directory assignments plus app-specific, server-side entitlements keyed by issuing tenant and object ID. Records include persona, identity source, sponsor, approval, expiry and allowed application. Never authorize by email or self-declared sign-up fields. Trips benefits need an employee/dependent relationship and benefit eligibility, not just authentication. The PoC demonstrates this separation with synthetic data.

Sponsored registration is implemented and configured, with one authorized personal-email send confirmed by ACS `Succeeded` and live sent status; inbox receipt/account setup/redemption remain pending. Only approved, enabled Caldova workforce members may act: app01 Employee may invite a dependent; app02 additionally requires `admin` or `dependentRegistrant` for dependents and `admin` for the business section. The server checks current sponsor roles and benefit approval, binds the recipient's directory object, stores a token hash and enforces one-use redemption within at most 24 hours. Confirmation is an authenticated, CSRF-protected POST; an invitation session cannot access protected business pages. Dependent approval links to the current same-app benefit-eligible employee.

Site managed identities perform workforce Graph operations and Azure Communication Services email; a separate external-directory provisioner creates customer identities and assigns roles. Personal recipients receive a managed-sender invitation that opens email verification and password creation directly in the application. A separate public/native client, with no API permissions and attached to the signup-disabled flow, invokes the Microsoft native SSPR protocol for initial password setup on the pre-provisioned account. Native continuation tokens stay in the short-lived server session and are never used for app login; passwords and codes are never persisted. Normal sign-in remains MSAL code + PKCE. Passwords are not emailed. Verified organizational partners use one Graph B2B invitation with `sendInvitationMessage=false`, then ACS delivers its native `inviteRedeemUrl`. Signed home-issuer evidence and current app02 approval remain mandatory. See [REGISTRATION.md](REGISTRATION.md).

The driver opens with an interactive architecture view, source-file reader and 12-step runbook. Its hosted version uses a separate workforce registration and App Service EasyAuth on **all URLs**, including assets, catalog, manifest and source ZIP, with an admin operator object-ID allowlist. The full offline copy needs no authentication or network except optional portal/reference operations. It contains synthetic defaults and no credentials or real governance records. The three sites use Windows B1/IIS in one isolated Oguzhan resource group alongside the dedicated External ID directory resource.

Credentials, recipient records and deployment inventories stay private. Replaceable configuration uses IIS-protected App_Data; runtime registration state uses `D:\home\data\multiidp\<appId>\registration-state.json` outside `wwwroot`, excluded from deployment ZIPs. A live ZIP deployment erased the former App_Data file with one unsent pending record and no approvals; no email had been sent. The corrected runtime record survived several later ZIP deployments in the live UI. Windows/IIS storage uses same-directory `MoveFileExW` replacement/write-through, a flushed writer and sidecar lock; commit failure retains a private recovery temp without a copy-overwrite or delete-then-move fallback. Deployment survival is separate from successful registration. The approved registration-policy exception affects one approved partner guest only; MFA remains required and other policy fields were preserved. Record builds, synthetic tests, HTTP challenges and actual admission separately. Email acceptance does not prove delivery or registration. OIDC establishes a claims identity; downstream Windows impersonation/Kerberos delegation remains a separate migration decision.
