Extend the working workforce PoC

Keep the existing ASP.NET application and its business screens. Extend its workforce authentication with a separate External ID provider, then apply the same application authorization to both identities. This guide documents the implementation built in Sampleapp01; adapt the named locations to the customer's project.

MVC controller names below are sample locations. For Web Forms, use the corresponding login page events, shared page base class and registration pages, or retain the sample's MVC registration endpoints beside the existing pages.

01 · Project and packages

Keep target framework net48. In an existing non-SDK project, install through NuGet; add the adapted source files as normal project items. Conversion to the sample's SDK project format is unnecessary. Retain compatible existing versions where possible and resolve binding redirects after the build.

PackageVersion tested here

Microsoft.Owin.Host.SystemWeb, Microsoft.Owin.Security.Cookies, Microsoft.Owin.Security.OpenIdConnect4.2.3

Set Startup.AppId to "sampleapp01". If copying the shared source unchanged, add SAMPLEAPP01 to the project's compilation constants; otherwise its conditional compilation selects Sampleapp02.

This sample uses Katana with an explicit MSAL adapter. Microsoft also provides Microsoft.Identity.Web.OWIN for Framework applications. Using that alternative requires its own dual-provider adaptation and verification.

02 · Directory registrations

Represent this application separately in each tenant, with assignment required. Keep the working workforce client and assign employees its Employee role. Create the External ID web client with Dependent, Retiree and External roles and associate its controlled EmailPassword flow. Public signup is disabled in this design.

  • Workforce callback: https://<application-host>/signin-workforce.
  • External callback: https://<application-host>/signin-external.
  • Each client uses its own credential and tenant-specific issuer. Web login uses authorization code with PKCE.

Sampleapp01 admits employees and approved customer personas. Organizational partner B2B belongs to Sampleapp02.

03 · Server configuration

ConfigurationLoader.Load("sampleapp01") reads MULTIIDP_SAMPLEAPP01_CONFIG: an absolute protected JSON path containing employee domains, both tenant/client IDs, exact issuers, callbacks and the entitlement path. Obtain each issuer from that tenant's discovery metadata.

Supply credentials only in the server environment: MULTIIDP_SAMPLEAPP01_WORKFORCE_SECRET and MULTIIDP_SAMPLEAPP01_EXTERNAL_SECRET. Registration has a separate MULTIIDP_SAMPLEAPP01_REGISTRATION_CONFIG and provisioner credential MULTIIDP_REGISTRATION_EXTERNAL_SECRET. Keep configuration in protected App_Data or outside the web root; durable invitation state stays outside deployment content.

04 · Authentication startup

Extend the existing Startup.Configuration(IAppBuilder) or Startup.Auth.cs; keep one OWIN startup entry point. Register the secure cookie first, then passive schemes named workforce and external, both issuing that cookie. Preserve the existing Global.asax initialization, routes and services. If retaining the sample MVC endpoints beside Web Forms, merge their routes and AntiforgeryFailureFilter registration into Application_Start.

Authority and MSAL integration — partial excerpts 
// Startup.AddProvider: separate client and settings for each tenant.
var authority = external
    ? "https://" + tenant.CiamDomain + "/" + tenant.TenantId
    : "https://login.microsoftonline.com/" + tenant.TenantId;
var msal = ConfidentialClientApplicationBuilder.Create(tenant.ClientId)
    .WithClientSecret(secret).WithAuthority(authority)
    .WithRedirectUri(tenant.RedirectUri).Build();
// OWIN Authority is authority + "/v2.0"; callbacks are distinct.

// MsalOpenIdConnectHandler.RedeemAuthorizationCodeAsync:
var result = await client.AcquireTokenByAuthorizationCode(new string[0], request.Code)
    .WithPkceCodeVerifier(verifier).ExecuteAsync().ConfigureAwait(false);

Port the complete MSAL adapter and strict validator. Katana retains protected state and nonce checks; the validator enforces signature, issuer, audience and lifetime. SecurityTokenValidated calls RegistrationSignInPolicy.Validate before admission or a restricted registration session. An access token is never displayed or stored in the application cookie.

05 · Login and logout

Replace the Windows-only entry point in the login controller or Web Forms button event. Validate the form/CSRF token, resolve the email hint using RegistrationRuntime.Route, and challenge only that scheme.

Login challenge — partial excerpt 
var source = RegistrationRuntime.Route(Startup.Config, email);
var properties = new AuthenticationProperties { RedirectUri = "/Benefits/Index" };
properties.Dictionary["login_hint"] = email.Trim();
HttpContext.GetOwinContext().Authentication.Challenge(properties,
    source == IdentitySource.Workforce ? "workforce" : "external");
return new HttpUnauthorizedResult(); // MVC action response

Employee domains route to workforce; other Sampleapp01 addresses route to External ID. Email is routing input, never proof of identity. A workforce error stays a workforce error. Logout is a CSRF-protected POST calling SignOut(Startup.CookieScheme).

06 · Existing user mapping

Replace lookups based on DOMAIN\username or email with an explicit mapping from validated tid + oid to the existing application user/employee key. The sample adds subject_key = tid + ":" + oid; app approvals are keyed by application, tenant and object ID.

Keep existing bookings and employee numbers. Store persona, sponsor, status, expiry and benefit eligibility beside the mapping. A dependent links to the workforce employee's stable IDs and requires a verified relationship plus a current, benefit-eligible same-app employee approval. Email changes must not create new access. Replace AD group assumptions with the explicit app roles and approval rules; connect production eligibility to the customer's employee/relationship data.

07 · Protected application paths

Apply a shared guard at every protected MVC action, service endpoint and API, or in a Web Forms base page's OnInit. Port the sample's benefit check into that guard:

var decision = RegistrationSignInPolicy.EvaluateApplicationAccess(
    Startup.Config, principal,
    RegistrationRuntime.ReadEntitlements(Startup.Config), DateTimeOffset.UtcNow);
// Deny/stop the request unless decision.Allowed.

Use the authenticated server principal. This check verifies the directory/source, signed persona role, current app approval and dependent eligibility. It rejects registration_only sessions. Menu visibility, [Authorize] or a role check alone does not apply these rules. Reload governance on protected requests so revocation takes effect.

08 · Dependent registration

Add the employee invitation page and recipient completion pages using RegistrationController, RegistrationRuntime and JsonInvitationStore. An approved workforce Employee with current benefit eligibility may invite a dependent; server checks apply to every POST.

  1. InviteAsync rechecks the sponsor, provisions/binds the External ID customer, assigns this app's Dependent role and emails the scoped invitation through ACS.
  2. PasswordSetupController.cs and PasswordSetup.cs verify email and let the recipient create a password. A separate native setup client uses Microsoft's native SSPR protocol for these pre-provisioned accounts; continuation state stays in a short server session. No password is emailed or persisted.
  3. Normal MSAL login establishes a registration-only session. CompletePost rechecks identity and sponsor, atomically consumes the invitation and records approval; a fresh sign-in grants ordinary access.

Home-page sign-in also resumes one unique current, sent invitation for the exact validated identity and app role. Invalid explicit links, duplicates and expired invitations fail. Keep CSRF protection, one-use token hashing and atomic storage; substitute a transactional production database for the PoC JSON store. Provisioning uses separate service permissions; interactive web login does not receive directory-write permissions.

Registration hosting: the current RegistrationServices.cs workforce Graph and ACS adapters require Azure App Service managed identity, its Graph application permissions and the ACS sender role. The external directory uses a separate provisioner. For VM or on-premises IIS, adapt token acquisition to a supported workload identity, certificate-backed service identity or secured registration service. The registration adapter cannot be copied unchanged to that host; ordinary OIDC login is independent of this dependency.

09 · IIS and Windows dependencies

On the isolated PoC IIS application, enable Anonymous authentication and disable Windows authentication so OIDC receives the request. Use an integrated CLR v4 application pool, HTTPS and <authentication mode="None" />; remove FormsAuthentication if it intercepts requests. Preserve secure cookies, OWIN startup detection and required binding redirects from web.config. Anonymous IIS entry does not authorize protected application actions.

Review inherited IIS/ASP.NET URL authorization rules so login, OIDC callbacks and recipient setup routes can reach their handlers. Enforce application access in the shared guard; old Windows group rules do not authorize an External ID customer.

Audit Windows impersonation, WindowsIdentity, SQL integrated security and file/service access. An OIDC claims principal does not provide a Kerberos ticket or downstream delegation. Choose and test an explicit service identity or another supported downstream access design before production migration.

Deploy first to a separate test IIS application. Preserve the existing production binaries, IIS authentication settings and configuration for rollback. Restore those together if needed; do not overwrite durable invitation/governance records or automatically resend invitations.
