Automatically resolve users across all workforce UPN domains

Sampleapp01 checks the entered sign-in name against users in the configured workforce tenant through Microsoft Graph. A matching workforce account selects employee sign-in. A successful lookup with no matching account selects External ID. The app then requires the signed identity, role and current approval.

Employee UPN / personal email→AccountController.Login→RegistrationRuntime.RouteAsync→Workforce Graph lookup→workforce / external challenge→Entra → callback → app approval

This walkthrough covers Sampleapp01. The excerpts show its path through the shared source files. Filenames and line numbers come from the deployed source catalog; open the complete linked file for implementation.

01 · Query the workforce directory before sign-in

The tenant can contain 100 different verified UPN domains. The server looks up the exact entered userPrincipalName in that tenant's user collection. There is no per-domain routing list to maintain for Sampleapp01.

For example, employees using company.example, subsidiary.example and the initial onmicrosoft.com domain all resolve through the same lookup. Adding another domain or employee in Entra does not require another provider or domain entry in this app.

The application backend uses its workforce managed identity with Microsoft Graph User.Read.All. The hosted PoC already uses that permission for sponsor checks. The confidential interactive login clients keep their sign-in scopes; the browser never receives a Graph service token. Other IIS hosts must provide an approved server-side Graph credential adapter.

  • Keep one workforce authority: https://login.microsoftonline.com/<workforce-tenant-id>. Every workforce UPN uses that same tenant, client and /signin-workforce callback.
  • Enter the account's UPN. Each account has one UPN; SMTP aliases are separate. This resolver performs exact UPN lookup, so an alias is not automatically treated as another sign-in name. Alternate email sign-in would require a separately agreed resolver and Entra configuration.
  • Changing the UPN on the same account preserves its object ID. Approval and dependent links use tenant ID + object ID. Creating a replacement account creates a new identity requiring its own approval.

03 · The Graph result selects workforce or External ID

RegistrationRuntime.RouteAsync connects Sampleapp01's lookup to the existing workforce service identity. WorkforceAccountResolver.ResolveAsync validates the entered UPN and queries Microsoft Graph.

The query matches the complete UPN, not a domain suffix. The resolver checks the returned identifier and object ID. Only a successful, well-formed empty result selects External ID. A directory error, malformed response or multiple matches stops routing.

A matching disabled or guest account still selects workforce. Authentication and Sampleapp01's Employee role and approval requirements determine access. If an identifier exists in both directories, ordinary login chooses workforce; a dependent invitation remains bound to its external identity.

06 · A dependent invitation selects its bound external identity

An approved Employee with current benefit eligibility opens Invite someone in Sampleapp01, enters the dependent's personal email and confirms the relationship. The service provisions or reuses the external customer, assigns Dependent for this app and sends a secure, expiring invitation.

A new recipient verifies email and creates a password through the invitation. An existing recipient can use existing-account sign-in. RegistrationController.Begin challenges the invitation's stored source directly; the employee's own UPN suffix does not control the dependent's route.

07 · A failed sign-in stays in the selected realm

The failure handler redirects to /Account/Failure. It never challenges the other provider. Initial lookup failure returns HTTP 503 before sign-in. Once workforce is selected, resolve credentials, assignments and sign-in policy in that directory.
