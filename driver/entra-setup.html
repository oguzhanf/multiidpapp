From tenant setup to an approved login

Follow the steps in order. Each step names the directory, the setting and the result to check. If the customer already has an External ID tenant, verify it in step 01 and continue with its app registrations.

This is the configuration for the implementation in this driver. The four web clients use OWIN + MSAL authorization code with PKCE. Personal identities use the external tenant; employees and App02 organizational guests use the workforce tenant.

Have ready

Administrator access in both directories; an approved Azure subscription and one PoC resource group; HTTPS origins for both apps and the driver; approved employee test accounts, partner home tenant and recipient emails; an access expiry and benefit-eligibility rule.

In the Caldova lab, hosting and email are in Oguzhan / rg-caldova-multiidp-poc. Use the customer's approved equivalents onsite. Full scripted setup uses a delegated Global Administrator in each tenant and Azure rights to create resources, custom roles and role assignments. A workforce Global Administrator does not automatically have those Azure permissions.

01 · Create or verify the External ID tenant

Directory: workforce for creation → external for configuration

  1. Open Microsoft Entra admin center. Go to Entra ID → Overview → Manage tenants → Create.
  2. Select External. For subscription-backed setup, select Use Azure Subscription, enter the tenant name, initial domain and agreed country/region.
  3. Select the approved subscription and the same PoC resource group used for hosting. Review and create; wait for provisioning to finish.
  4. Switch directory through Directories + subscriptions. On the external tenant's Overview page, record its tenant ID and primary domain. Confirm the customer controls administration, billing and ownership.

If the tenant already exists, start at item 4. Use an External ID external tenant for customer accounts. The third party's legacy B2C tenant is outside this setup.

Check: the selected directory is the customer external tenant and its ID differs from the workforce tenant.

03 · Register the two External ID web clients

Directory: external

  1. Go to Entra ID → App registrations → New registration. Name the first client sampleapp01-external; select accounts in this directory only.
  2. Choose platform Web and set https://<app01-host>/signin-external. Register and record the client and application object IDs.
  3. Under Authentication, verify the exact HTTPS callback. Leave implicit access-token and ID-token issuance disabled. Keep public client flows disabled for this confidential web client.
  4. Under Certificates & secrets, configure the server credential. For the PoC, store the secret value securely at creation and record expiry; production credential management needs customer agreement.
  5. Under API permissions, configure delegated identity scopes openid, profile, email and offline_access and grant administrator consent. The sample does not require delegated User.Read or directory-write permissions for web sign-in.
  6. Repeat for sampleapp02-external, using https://<app02-host>/signin-external and a separate credential.

The repository's Configure-PocApplications.ps1 -TenantKind External creates both clients and their private manifests. If using that route, run it to create the clients and use these portal steps to inspect the result; portal-created clients cannot be silently adopted by the script.

Check: both external clients are single-directory Web apps with different IDs, credentials and callbacks.

Microsoft: register an application in the external tenant

04 · Define customer roles and require assignment

Directory: external · repeat for App01 and App02

  1. Open each App registration → App roles → Create app role. Create enabled roles with exact values Retiree, Dependent and External; allowed member type Users/Groups.
  2. Go to Enterprise applications, open the corresponding app, then Properties → Assignment required? → Yes. Keep Enabled for users to sign-in enabled.
  3. In Users and groups → Add user/group, an administrator can assign an existing customer its intended role. In the employee invitation flow, the provisioner creates or finds the customer and assigns the target app's role.

Roles are defined on App registrations and assigned on Enterprise applications. Assigning Dependent in App01 does not assign it in App02. Role assignment establishes the persona; application approval is recorded when the invitation is confirmed.

Check: assignment required is enabled on both enterprise apps. In step 15, test with an ordinary non-admin customer: an unassigned customer is rejected; a role-assigned customer with no current app approval cannot open business pages.

Microsoft: app roles for customer applications

05 · Associate a controlled email/password user flow

Directory: external

  1. Go to Entra ID → External Identities → User flows → New user flow. Give the flow a clear name, such as MultiIdpNet48ControlledSignIn.
  2. Select Email with password. Collect only agreed customer attributes; benefit relationships and application entitlements remain in the app's governance records.
  3. Open the flow, then Use → Applications → Add application. Add both external web clients. An application can belong to only one user flow.
  4. Disable public signup through Microsoft Graph: set onInteractiveAuthFlowStart.isSignUpAllowed to false. The portal creates a sign-up/sign-in flow; the signup restriction requires the Graph configuration below or the supplied setup script.
  5. Read the flow back and verify both client associations, EmailPassword-OAUTH and disabled signup.
Graph configuration for invitation-only sign-in

Use a privileged setup session in the external tenant with EventListener.ReadWrite.All. Retrieve the flow ID from GET /v1.0/identity/authenticationEventsFlows; match its name and application associations.

PATCH https://graph.microsoft.com/v1.0/identity/authenticationEventsFlows/<flow-id>
{
  "@odata.type": "#microsoft.graph.externalUsersSelfServiceSignUpEventsFlow",
  "onInteractiveAuthFlowStart": {
    "@odata.type": "#microsoft.graph.onInteractiveAuthFlowStartExternalUsersSelfServiceSignUp",
    "isSignUpAllowed": false
  }
}

The tested Configure-PocExternalFlow.ps1 uses Graph v1.0. Microsoft's disable-signup how-to also shows a beta example. Add associations individually through /conditions/applications/includeApplications when using Graph.

Check: an uninvited personal email cannot self-register from the normal login screen. Provisioned customers can sign in through the selected flow.

Microsoft: create a user flow · Disable public signup · Graph v1.0 update API

06 · Register the two workforce web clients

Directory: workforce · switch directory before continuing

  1. Create sampleapp01-workforce and sampleapp02-workforce in App registrations, each single-directory and platform Web.
  2. Set the respective callbacks to https://<app01-host>/signin-workforce and https://<app02-host>/signin-workforce. Configure separate server credentials, the same identity scopes and administrator consent as step 03.
  3. Leave implicit grants and public client flows disabled. Under each enterprise application's Properties, set assignment required to Yes.
  4. Define the enabled user app roles listed below. Values are case-sensitive; use admin and dependentRegistrant exactly.
  5. Under Token configuration → Add optional claim → ID token, add idp to the workforce clients. App02 requires this signed claim to validate a partner's home organization.
Workforce clientRole valuesPurpose
Sampleapp01EmployeeEmployee access and eligible dependent sponsorship
Sampleapp02Employee, Partner, admin, dependentRegistrantEmployee / guest personas and employee-only registration capabilities

App02 B2B guests authenticate in their home organization and receive a token for the workforce resource tenant. The resource app stays single-directory; there is no common or organizations authority in this implementation.

Check: four separate web clients now exist across two tenants. App01 has no workforce Partner role.

07 · Assign employees and registration capabilities

Directory: workforce · application: approval store

  1. Choose enabled workforce Member accounts. Under each target Enterprise application → Users and groups → Add user/group, assign Employee.
  2. Create a current employee approval for that app using the workforce tenant ID and user object ID, expiry and benefit eligibility. The repository's Add-PocAssignment.ps1 performs both role assignment and private entitlement recording.
  3. For App02, assign additional capabilities only to approved employees. Select each role separately; an admin assignment does not replace Employee.
  4. After deployment, sign out and sign in again after role changes. Confirm the registration sections visible to each account during step 15.
ActionRequired workforce app rolesAdditional check
App01: invite a dependentEmployeeCurrent eligible employee approval and relationship confirmation
App02: invite a dependentEmployee + (admin or dependentRegistrant)Same employee eligibility and relationship check
App02: invite a vendor / business partnerEmployee + adminCurrent approval, accountable sponsor and business purpose

Guests and external customers cannot act as employee registrants. Enterprise app roles are distinct from Entra administrator roles. The application refreshes the sponsor's directory state and roles when sending or confirming an invitation.

Employee approval when configuring the client manually

Seed an approved employee record in the protected entitlement file, repeat it for App02 and each approved employee, and set the identity configuration's entitlementFile to the deployed absolute path. A local file change alone does not update Azure.

Check now: Employee and capability assignments match the intended users and approvals. Check in step 15: App02 Employee alone has no registration capability; dependentRegistrant sees only dependent registration; admin sees dependent and business registration.

Microsoft: assign users and roles

08 · Prepare App02 organizational B2B access

Directory: workforce · partner home tenant: separate organization

  1. Under External Identities → External collaboration settings, review invitation permissions and collaboration restrictions for the approved partner domain.
  2. Under External Identities → Cross-tenant access settings → Organizational settings, review the approved partner tenant's inbound B2B collaboration settings. Agree any home-tenant MFA trust with its administrator.
  3. Prepare an approved Employee with admin and a partner test account. Send the invitation during step 15, after services and application deployment are complete.
  4. At that point, use App02's Invite someone → vendor / business partner section and enter the organizational email. The service resolves a candidate Entra organization, creates a workforce B2B invitation, binds the guest, assigns App02 Partner and emails Graph's native redemption link.
  5. During the acceptance test, the partner redeems with the expected home work account, completes required MFA and confirms registration. App02 records approval after verifying the signed home issuer.

For personal vendor addresses, App02 uses the External ID customer path in steps 09–11. An email domain or discovery result is a routing hint; it does not prove organizational membership or a Microsoft 365 licence. A workforce sign-in failure never falls back to External ID.

Check now: the partner organization is permitted by workforce collaboration policy. Check in step 15: the redeemed guest has App02 Partner assignment and signed home-organization evidence, and has no App01 approval.

Microsoft: B2B cross-tenant settings · B2B invitation and redemption URL

09 · Configure separate registration service identities

Directory: workforce + external · Azure: same PoC resource group

  1. For the hosted PoC, create Windows App Service hosting for both net48 applications in the same resource group. Set ASP.NET V4.8, HTTPS-only and TLS 1.2 or later. Enable each site's Identity → System assigned → On; record the workforce managed identity object ID.
  2. Grant the managed identities the workforce Graph application permissions below through an administrator setup session. Managed identities are service principals; these grants are separate from interactive web-client consent.
  3. In the external tenant, create the dedicated MultiIdp Net48 registration provisioner, configure its private server credential and grant only its listed Graph application permissions with administrator consent.
  4. Record the target enterprise app object IDs and role GUIDs in each private registration configuration. The service must assign the correct role to the correct target app.
  5. Disable HTTP URL request logs, failed-request tracing and detailed error logging on the sample sites before invitations. The PoC deployment script refuses these settings because URLs can contain invitation bearer tokens. Keep safe operational audits separate.
Runtime identityGraph application permissions in this PoC
App01 workforce managed identityApplication.Read.All, User.Read.All
App02 workforce managed identitySame read permissions + AppRoleAssignment.ReadWrite.All, User.Invite.All
External customer provisionerUser.ReadWrite.All, Application.Read.All, AppRoleAssignment.ReadWrite.All

These are tenant-wide application permissions held by the registration services. Scope their use in code to the owned PoC clients; protect credentials and review the service boundary for production. None of these provisioning grants belongs on the four interactive clients. Configure-PocRegistration.ps1 applies and verifies the listed grants.

Graph application-permission grants require a privileged setup administrator and the relevant consent scopes; the runtime permission table is not the administrator's delegated scope list. Microsoft: grant a service principal an app role

Check: service-token calls can read sponsor state, create the intended customer / guest and assign its persona; ordinary web login cannot write directory data.

10 · Configure the Azure-managed invitation sender

Azure: workforce subscription · same PoC resource group

  1. In Azure, create Email Communication Services and provision an Azure-managed domain. Wait for verification and record its generated sender address.
  2. Create Azure Communication Services in the same resource group. Connect the managed email domain and record the HTTPS communication endpoint.
  3. Grant both sample sites' managed identities the resource-scoped mail permissions. The supplied script creates a custom role containing Microsoft.Communication/CommunicationServices/read and write, assigned only on that communication resource.
  4. Set the sender and endpoint in private per-app registration configuration. Send the actual invitation and verify delivery with an approved test recipient during step 15, after password setup and app deployment.

The application sends a bound, single-use HTTPS invitation lasting at most 24 hours, capped by the access deadline. For B2B it calls Graph once with sendInvitationMessage=false and emails the returned inviteRedeemUrl. For personal email it sends its own External ID registration link. Passwords are never emailed.

Check now: the verified domain is connected and runtime sender permissions are assigned. Check in step 15: the recipient receives the expected app's email. A provider-accepted send alone is not proof of delivery or completed registration.

Microsoft: create email resources · Send email

11 · Enable invited users to verify email and create a password

Directory: external · client: separate native setup registration

  1. Under Entra ID → Authentication methods → Policies → Email OTP, enable the email method for the intended customer users. The PoC script explicitly enables all users in this dedicated external tenant and refuses exclusions; review the intended scope before applying it.
  2. Create a separate single-directory app named MultiIdp Net48 invitation password setup. Under Authentication → Redirect URI configuration, set Enable the following mobile and desktop flows and Enable native authentication to Yes, then save. The older label for the first setting is Allow public client flows. Leave API permissions empty; no client secret is needed.
  3. Add this setup client to the same controlled EmailPassword user flow. Keep public signup disabled; the native client is separate from the confidential web sign-in clients.
  4. Store its client ID as external.passwordSetupClientId in both private registration configurations. With repository-managed state, run Configure-PocPasswordSetup.ps1 after Configure-PocRegistration.ps1.
  5. During step 15, open an approved personal invitation: Verify email and create password → verify Microsoft's email code → Create your password → normal sign-in → Confirm registration. An existing customer can select existing-account sign-in.

The backend pre-provisions an email/password customer with an unknown random password. Initial password creation uses Microsoft's native SSPR API behind the invitation's Create your password screens. This is an account-setup extension to MSAL web login. Codes, passwords and native continuation tokens are never recorded in source or logs.

Administrator setup permission for the Email OTP policy

The temporary delegated setup session needs Policy.ReadWrite.AuthenticationMethod, an appropriate administrator role and the external tenant. Use the same external administrator as the Azure CLI setup session. The runtime provisioner has no policy-write permission.

Connect-MgGraph -TenantId $externalTenantId `
  -Scopes Policy.ReadWrite.AuthenticationMethod,User.Read `
  -ContextScope Process

# In the same PowerShell process, run registration setup with:
# -EnableExternalEmailPasswordReset -UseMicrosoftGraphPolicyContext

Check now: Email OTP is enabled and the native client is associated and configured. Check in step 15: the invited user creates their own password from the invitation, then confirms app registration. There is no instruction to select Forgot password.

12 · Verify sign-in policies and MFA in both directories

Directory: workforce and external, checked separately

  1. Review Protection → Conditional Access and the authentication methods allowed in each tenant. Confirm licensing and the external tenant's supported policy features.
  2. Target the appropriate enterprise applications and intended personas. Test employees, customers and B2B guests against the agreed security requirements.
  3. For partners, check security-information registration and cross-tenant trust before the onsite demonstration. A home work account still needs to meet resource-tenant policy.
  4. On failure, inspect Monitoring & health → Sign-in logs in the tenant that issued the token, then the application's own denial reason. Resolve assignment, consent, MFA or policy problems at that boundary.

Check: permitted personas complete required MFA; blocked sign-ins stay blocked and do not switch identity realms.

Microsoft: external-tenant feature support

13 · Connect the .NET Framework 4.8 applications

Application server: IIS / Windows App Service

  1. Record both clients, tenant IDs, exact redirect URIs and exact token issuers per app. Read the issuers from each tenant's OIDC discovery document.
  2. Configure employee domains and approved partner routes. App01 routes employees to workforce and customers to external; App02 also supports approved workforce B2B partners.
  3. Supply confidential-client secrets in server environment settings. Set the private identity and registration JSON paths; preserve durable invitation/approval state outside deployment content.
  4. Deploy the net48 application changes described in Modify an existing .NET 4.8 application. Both providers must validate signature, issuer, audience, lifetime, nonce and state before creating the shared application cookie.
  5. Verify current approval by app + tenant ID + object ID, persona role, expiry, and dependent / partner rules on protected application requests.

14 · Protect the driver with its own workforce registration

Directory: workforce · Azure: driver App Service

  1. Create a fifth, separate workforce app registration for the driver. Configure the Web callback https://<driver-host>/.auth/login/aad/callback.
  2. In Driver App Service → Authentication, configure Microsoft Entra using the workforce tenant and this driver client. Require authentication and redirect unauthenticated requests to Entra.
  3. Define the enabled user role DriverAccess, require assignment on its enterprise app and assign the operator to that role. Restrict App Service's allowed principals to the intended workforce operator object ID; leave no anonymous excluded paths.
  4. Verify pages, assets, settings, code catalogs and source downloads are protected. Secure-PocDriver.ps1 configures the dedicated EasyAuth client and operator allowlist.

The driver's EasyAuth hybrid login enables ID-token issuance on that driver registration only. The four demo web clients retain authorization code + PKCE. Caldova's live driver is restricted to its configured administrator; sample-app admin does not grant driver access.

Check: the approved operator can open this guide; anonymous visitors and other identities cannot read any hosted driver content.

The hosting/deployment scripts retain the caldova- site-name prefix and vary NameSuffix; adapt them if customer site names differ. The initializer uses the default state folder and has no existing-tenant mode.

For unchanged automation, use https://caldova-sampleapp01-<suffix>.azurewebsites.net and the App02 equivalent as the registered origins. Registration setup verifies those origins against the sites. An existing IIS application can use its own origins for interactive login, but the App Service managed-identity registration backend needs adaptation. ARM and workforce Graph setup sessions must use the same workforce operator.

Script-created PoC credentials expire after seven days. Scripts refuse expired or untracked credentials and do not rotate automatically. Arrange explicit credential rotation and update protected saved state and server settings before a later demonstration. Keep the private state directory and its protected credentials outside Git and deployment source downloads.
